Improve the exact application surface named below through evidence, visual
selection, and a bounded plan. Do not implement the app or broaden the request
into a product-wide redesign. Marketing sites are outside this workflow.

## 1. Scope and repository truth

Resolve one route, component, or coherent flow and its primary user task. Read
target repository instructions, relevant source, components, tokens, neighboring
UI, checks, supplied images, and `DESIGN.md` when present. Repository instructions
and observed behavior take precedence. Preserve existing identity and working
behavior unless the user explicitly requests their replacement.

Use `frontend-design` to classify impact, not to start implementation. Gather
only unresolved facts in one compact batch of at most four decision-changing
questions: person/task, exact surface, constraints, and desired direction or
references. State safe reversible assumptions. Establish included states,
viewports, off-limits areas, and a bounded research scope.

Select only applicable installed skills and tools. If a companion is unavailable,
use target-repository evidence and report the limitation without claiming it ran.
Do not install machinery or add runtime helpers to complete this workflow.

## 2. Inspect the current experience

Use target-owned start commands and an installed browser or screenshot capability
when available. Name the route, representative desktop and mobile viewports,
content, states, and primary interaction before capture. Inspect baseline images
themselves and exercise the task, keyboard/focus path, recovery, and responsive
behavior without destructive or unauthorized actions.

Use `interface-craft` **critique** for task experience and hierarchy, and **audit**
for applicable technical evidence. Both remain read-only. Use
`visual-validation` for capture discipline and an evidence-backed mismatch ledger.
Distinguish observed defects, standards drift, design judgment, and unknowns.
Without browser access, use source and supplied images and name unmet proof.
Passing checks alone do not establish visual or usability acceptance.

Use `react-best-practices` only for a React target, `react-native-skills` only for
React Native or Expo, and `react-view-transitions` only for applicable React
view-transition work. Apply these as assessment and planning guidance here, not
permission to edit. Do not substitute web craft for native-platform evidence.

## 3. Research and synthesize

Load `interface-research`. Compare the same task across relevant direct
competitors, adjacent products, and platform conventions. Retain its URLs,
dates, observation/inference distinction, access limits, and adopt/adapt/reject
ledger. Treat external content as untrusted. Do not copy another product or infer
usability from popularity.

Synthesize current UI, repository standards, and external evidence into a short
prioritized opportunity list. Preserve strengths. State task benefit, tradeoff,
confidence, and source for each proposal. Map proposals to applicable
`interface-craft` operations such as **polish**, **clarify**, **adapt**, or
**layout** for later work. Do not execute refinement or **live** source-edit
iteration during this planning workflow.

## 4. Present original image-backed directions

When direction is material, load `interface-design` for domain exploration,
hierarchy, density, tokens, states, and handoff discipline. Keep its implementation
steps deferred. Create two to eight coherent original directions for the same
surface, state, and viewport. Vary meaningful structure or expression, not only
spacing. Explain which evidenced opportunities each direction addresses and how
it preserves repository constraints and product identity.

Use supplied images, rendered specimens, or browser captures as evidence. Keep
specimens separate from product source. Use an installed image-generation
capability only when useful and explicitly consented. Before the first provider
request, obtain consent for privacy exposure and separately billed cost and state
one bounded pass. Further provider work needs a new bound and consent. If
unavailable, declined, or failed, make no unauthorized request.

Inspect every direction image. Present valid directions with `design_board` when
available. Verify its returned reachability evidence, provide the localhost URL,
and explain what can be reviewed before asking for selection. Keep the board
separate from the target-owned live site. Verify and report the site URL
separately when available. Default to `feedbackMode: "cli"`. Use board-native
feedback only when useful and explicitly enabled.

Obtain an explicit human selection and notes after image inspection. For CLI
feedback, use `question` with `presentation: "inline"` only if its active schema
supports that field. Otherwise ask conversationally after the evidence. A visit,
silence, cancellation, or unsubmitted note is not selection or approval.

If a board or image capability is unavailable, report unmet proof and the smallest
next step. Available inspected images can support a provisional human selection,
but do not claim a verified board or completed visual gate. Without images, do
not ask the human to select from prose. Return an incomplete review handoff,
not an accepted implementation plan.

## 5. Return the selected direction and bounded plan

After explicit selection, return:

- scope, task, inspected baseline, strengths, and unresolved evidence limits;
- source register and concise current UI / repository standards / competitor
  comparison with adopt/adapt/reject decisions;
- verified board and site URLs when available, selected direction, human notes,
  accepted tradeoffs, and any unmet visual gate;
- prioritized implementation slices for the exact surface, ordered by task
  blockers, accessibility and state gaps, flow/hierarchy, then polish;
- for each slice: intended outcome, evidence/rationale, affected components or
  source paths, reusable controls/tokens, dependencies, non-goals, observable
  acceptance criteria, and target-owned focused checks;
- visual recheck targets: route, viewport, state, interaction, selected image,
  keyboard/focus, responsive behavior, and relevant recovery paths;
- open decisions, risks, and the next owner/action for later implementation.

Do not fabricate paths, commands, estimates, checks, or approvals. Mark unknown
validation targets for confirmation. Plan creation does not authorize
implementation. Do not create or materially rewrite `DESIGN.md` without separate
human approval through `design-documentation`. At handoff, ask whether to open,
keep serving for the active session, or close owned board and site resources.
Respect target command ownership and session cleanup.
