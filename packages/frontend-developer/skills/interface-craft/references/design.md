# Design

Use `design` to establish or materially revise a deliberate web-interface
direction. It routes into the repository-native `/design` workflow and its
installed interface-design, frontend-design, image, and visual-validation
capabilities when they are available. It does not create a substitute command,
runtime, or state model.

## Establish the brief

Read target repository instructions, product constraints, existing screens,
representative source, tokens, components, and `DESIGN.md` when present. Resolve
the people using the surface, their task, the surface mode, the focal workflow,
content and state constraints, responsive needs, and the requested degree of
change. Separate established facts from assumptions. A missing design document
does not permit replacement of a coherent incumbent identity.

Name the decisions that matter before producing pixels: information hierarchy,
layout topology, density, type character, palette roles, contrast, depth,
shape, imagery stance, control behavior, motion, and the distinctive detail that
would make this product recognizable. State generic defaults and category habits
the brief rejects. Preserve product truth, factual copy, accessible native
controls, and target-framework constraints.

## Explore with evidence

For a material direction, use the native workflow to compare two to eight
coherent image-backed directions before asking for a visual choice. Each
candidate must answer the same user task while making a meaningfully different
commitment; do not present cosmetic variations as options. Keep captured
viewport, content, and state comparable. When browser, image, or board evidence
is unavailable, describe the missing proof rather than fabricating a result.

Present the visible facts, each direction's rationale, its tradeoffs, and the
specific decision requested. An explicit selection is required for a material
new direction. Silence, a preview visit, and a cancelled question are not
approval. Keep a target-owned site distinct from any review board and use only
installed capabilities and target-owned commands.

## Record and implement

Record accepted hierarchy, palette roles, typography, density, layout,
responsive behavior, depth, interaction states, motion, and signature choices.
If durable system guidance is needed, route to `document`; that operation owns
the approval-gated `DESIGN.md` process. For an implementation that changes
behavior, follow the target repository's normal engineering workflow. Keep
mechanical visual edits narrow and preserve the requested scope.

## Completion

A direction is complete when it is product-specific, accepted when material,
traceable to inspected evidence, and explicit about unresolved decisions and
unmet proof. Recheck the implemented result at representative sizes and states,
then report the chosen direction, source scope, verification evidence, and the
smallest next step for anything unavailable.
