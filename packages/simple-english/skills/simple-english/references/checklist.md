# Verification checklist

Use this checklist after the document is technically correct.

## Mechanical checks

Search prose outside code blocks and quotations for these patterns:

| Pattern                                  | Problem                      | Revision                                                  |
| ---------------------------------------- | ---------------------------- | --------------------------------------------------------- |
| `n't`, `'ll`, `'re`, `'ve`               | Contraction                  | Write the complete words.                                 |
| Semicolon                                | Joined instructions or facts | Use two sentences or a list.                              |
| `should`                                 | Weak obligation              | Use `must`, `can`, or a direct instruction when accurate. |
| Mid-sentence `if` or `when`              | Late condition               | Put the condition before the instruction.                 |
| `it`, `this`, or `they`                  | Possible vague reference     | Name the item when the reference is not unique.           |
| `verify`, `check`, `confirm`, `validate` | Possible synonym rotation    | Select one accurate term for the document.                |

Do not change a protected token only because it matches a pattern.

## Countable checks

1. Keep a procedural sentence at 20 words or fewer when practical.
2. Keep a descriptive sentence at 25 words or fewer when practical.
3. Put one instruction in each procedural sentence.
4. Keep one topic in each descriptive paragraph.
5. Keep a descriptive paragraph at six sentences or fewer.
6. Break a long list into parallel vertical items.

Sentence limits guide pragmatic writing. Do not damage a technical contract only
to meet a number.

## Meaning checks

- Does the revision preserve every requirement, boundary, risk, and exception?
- Does each important concept use one consistent term?
- Does each pronoun have one clear reference?
- Does active voice identify the actor when the actor matters?
- Does each condition occur before its instruction?
- Does each warning occur before the risky action?
- Does evidence stay beside the claim that it supports?
- Are code, identifiers, commands, paths, URLs, quotations, and citations
  unchanged?
- Are required headings, frontmatter, checkboxes, and normative words unchanged?

## Delivery checks

- Lead with the result or purpose.
- Remove filler and repeated conclusions.
- Keep necessary domain terms.
- Explain a necessary uncommon term once.
- Keep conversational text natural when strict form adds no clarity.
- Do not claim ASD-STE100 compliance from this checklist alone.

## Check-mode report

For each material problem, quote the original text, name the rule in `SKILL.md`,
and give one compliant rewrite. Do not invent external rule numbers.
